# Camera System 端到端稳定性审查设计

## 目标

以 Jetson Orin Nano / JetPack 5.1.1 为生产验收环境，沿“摄像头采集 →
8 图任务生成 → HTTP 上传与重建 → PLY 下载与发布 → Q3D 展示”数据流，
系统审查并修复会导致崩溃、卡死、数据丢失、无法取消、资源泄漏或不可恢复
错误的高置信度缺陷。在稳定性得到证据保障后，再处理能够量化的性能瓶颈。

桌面和无硬件环境用于快速自动化回归，不能替代 Jetson 的摄像头、Qt 事件循环、
GStreamer/NVIDIA 编解码和 OpenGL 硬件验证。

## 审查策略

采用风险驱动的纵向审查，而不是先重构某个完整子系统。每一批从真实用户流程
选择一个最高风险边界，按以下顺序推进：

1. 建立当前失败或风险的可观测证据。
2. 追踪错误值、阻塞调用或资源所有权到最初来源。
3. 编写能够捕获该具体回归的失败测试。
4. 实施解决根因的最小生产改动。
5. 运行局部测试、完整自动化测试和适用的 Jetson 硬件门禁。
6. 记录仍未验证的外部依赖或硬件条件，不用间接证据宣称已完成。

现有未提交改动视为当前工作状态，必须保留。审查只修改与已证明缺陷直接相关的
文件，不顺手格式化、重命名或重构无关代码。

## 数据流和边界

### 1. 摄像头采集与录制

`multiwebcam` 负责设备发现、帧生产、预览、质量检测、快照和录制。审查重点：

- 设备启动、断开、重连和关闭不能阻塞 Qt GUI 线程。
- 帧队列必须有明确容量和丢帧策略，消费者变慢时内存不能无界增长。
- 停止、取消和异常路径必须终止生产线程、推理子进程及编码器。
- 录制结果和时间戳只在成功完成后可见；失败不能留下被误认为完整的输出。
- 多摄像头部分失败必须产生结构化状态，健康设备不因单路失败失去清理机会。

### 2. 任务打包与传输

`Tx_Rx` 负责 staging、manifest、上传、轮询、Range 下载、校验和 ACK。审查重点：

- 只上传经过二次 manifest/hash 校验的完整八图任务。
- 所有网络操作具有有限超时，取消信号能穿过健康检查、上传、轮询和下载。
- 重试只能用于幂等步骤；开始重建和 ACK 不能因盲目重试产生重复副作用。
- Range 响应必须验证状态码、区间、总长度、分片长度和最终哈希。
- PLY 使用临时文件写入并原子发布；中断或校验失败时不得暴露半成品。

### 3. 应用编排与 Qt 生命周期

`camera_system_app` 负责连接采集、传输和查看器。审查重点：

- UI 槽只更新界面或提交后台任务，不执行设备、网络、哈希或大文件解析。
- worker 的完成、失败、取消和销毁路径必须互斥且可重复调用。
- 页面切换、窗口关闭和异常退出必须停止定时器并回收线程、子进程与 GL 资源。
- 过期 worker 的信号不能覆盖新任务状态或加载错误的结果。
- 用户可见错误保留可操作原因，日志保留底层异常链且不包含敏感配置。

### 4. PLY 校验与 Q3D 展示

Q3D 路径负责 CPU 校验、GPU 上传、渲染和鼠标交互。审查重点：

- PLY 的类型、字段、数量、有限数值和边界在进入 GPU 前验证。
- 大文件读取、数据转换和统计计算不能长期占用 GUI 线程。
- Gaussian 缓冲区的布局、索引和 dispatch/draw 数量必须一致且有边界保护。
- 鼠标交互期间使用有界预览负载；交互结束不能触发不受控的全量 GPU 排序。
- OpenGL 对象仅在拥有其 context 的线程创建和销毁，重复释放必须安全。

## 错误处理

错误分为三类：

- 可恢复：单摄像头离线、暂时网络失败、用户取消。保持应用可操作，并允许重试。
- 当前任务失败：manifest、哈希、PLY 或协议校验失败。终止当前任务，清理临时
  产物，不破坏之前成功结果。
- 进程级不可继续：Qt/OpenGL 初始化失败或核心配置损坏。阻止进入对应功能，
  显示明确原因，但其他独立页面仍应可用。

后台异常通过结构化结果或 Qt 信号跨边界传递。禁止静默吞掉异常；也禁止在已知
可恢复错误上直接终止整个应用。

## 性能与资源指标

优化必须针对测得的瓶颈，并至少满足以下不变量：

- 生产者队列和 UI 待处理帧数量有固定上限。
- 空闲页面不持续轮询或重绘。
- 用户取消或应用关闭后，项目拥有的 worker、录制器和推理子进程在 5 秒内退出。
- 网络请求均配置连接和读取超时；状态轮询不会形成忙循环。
- Q3D 交互帧使用有界 Gaussian 数量，GPU 排序规模超过明确上限时降级而不是
  独占设备。
- 大文件、GPU 和帧缓冲资源有唯一所有者，完成、失败与取消路径均释放。

帧率、延迟和内存优化使用已有指标或新增非阻塞计数器取证。没有前后测量的改动
不作为性能优化提交。

## 验证设计

### 快速自动化门禁

- `.venv-jetson/bin/python -m pytest -q`
- `git diff --check`
- 受影响模块的定向测试
- 可用时运行 Ruff；缺少工具时记录环境缺口，不临时扩大依赖范围

### 集成门禁

- Qt 真实事件循环下验证后台启动、取消、页面切换和关闭。
- 本地模拟 HTTP 服务覆盖上传、轮询、Range 下载、损坏响应和取消。
- 临时目录验证任务与 PLY 的原子发布、失败清理和旧结果保留。

### Jetson 硬件门禁

- 摄像头发现、目标分辨率/FPS、预览、录制、快照及推理 smoke。
- NVIDIA OpenGL 4.3 context、真实高阶 SH PLY、左键/右键/滚轮交互和资源释放。
- GStreamer/NVIDIA 插件及实际采用的编码后端诊断。

外部 WSL 重建服务不可用时，只能证明本地协议模拟通过；真实跨设备重建保持为
未验证项，不能用本地测试替代。

## 完成标准

一次审查批次只有在以下条件全部满足时完成：

1. 缺陷或瓶颈有明确根因证据。
2. 回归测试在修复前因预期原因失败，在修复后通过。
3. 完整自动化门禁没有新增失败。
4. 适用的 Jetson 硬件门禁通过，或被明确记录为尚缺外部条件。
5. 没有覆盖用户现有改动，也没有夹带无关重构。

整个端到端目标完成还要求四个边界均完成审查，所有已发现的阻塞级和重要级问题
得到修复或有用户明确接受的剩余风险，并完成一次可用条件下的 Jetson 端到端
验收。
