# Qt 开发面试技术文档：多摄像头采集系统完整流程版

最后更新：2026-07-08

## 这份文档怎么用

这份文档不是拿来“背标准答案”的。你真正在面试里要做到的是：面试官随便从项目里拎一个点问，你都能顺着项目流程讲下去，而不是只会说几句“用了多线程、用了信号槽”。

面试官一般不会满足于“我用了多线程、信号槽、录制、识别”。他大概率会继续往下问：

- 为什么这样设计。
- 用了什么底层机制。
- 如果不用这个方案，会出什么问题。
- 这个设计牺牲了什么，换来了什么。
- 出现卡顿、丢帧、设备错乱、文件损坏时，你怎么定位。

后面每个流程都尽量按这个顺序讲：

> 这个问题在项目里为什么会出现 -> 我用了什么办法 -> 背后的 Qt 或系统机制是什么 -> 更简单的方案为什么不稳 -> 如果面试官继续问，我怎么往深处讲。

先把一个容易翻车的点说在前面：这个项目本身是 Python 版本 Qt，也就是 PySide6。面试里不要硬说成纯 C++ Qt 项目。更稳的说法是：

> 这个项目是用 Python 版本 Qt 做的多摄像头采集工具。语言层面不是 C++，但它遇到的问题和 Qt 客户端开发很像：界面线程不能被硬件阻塞，后台任务不能直接改界面，多路实时数据要拆开调度，录制要处理缓冲和收尾，摄像头这种硬件设备还要考虑发现、身份绑定和异常恢复。

## 项目一句话

如果技术面试官让你一句话介绍，可以这样说：

> 这是一个面向三维重建数据采集的多 USB 摄像头 Qt 工具。它能同时预览多路画面、分路录制视频、记录时间戳、评估画面质量，并在 Jetson 上支持硬件编码和异步目标识别。难点不在“把摄像头打开”，而在多路实时画面来了以后怎么稳定调度。

如果对方不太懂技术，就别一上来讲线程和编码，可以这样说：

> 做三维重建之前，需要从多个角度拍摄稳定、清晰、时间可对齐的视频。如果现场画面糊、曝光差、角度漏拍，后面重建就会返工。这个工具就是帮助采集人员把多路视频稳定录下来，并在现场判断质量。

如果二面开始深挖，可以把格局稍微抬高一点：

> 我更愿意把它看成一个小型实时多媒体采集系统。同一批摄像头画面会被预览、录制、质量评估、时间戳记录和识别模块同时消费，但这些路径对延迟、完整性和资源占用的要求不同，所以必须拆开设计。

## 完整流程总览

讲项目时不要从“我做了哪个按钮”开始。更稳的是按系统运行顺序讲，像你带面试官走一遍程序：

1. 程序启动，加载项目配置。
2. 发现摄像头，确认哪些设备可用。
3. 把系统设备入口绑定到业务相机身份。
4. 创建采集会话，启动多路后台采集。
5. 单帧画面进入系统，带上时间、来源和帧序号。
6. 预览路径只保留最新画面，界面定时刷新。
7. 录制路径按相机分路写入，保留时间戳。
8. 质量评估路径计算清晰度、曝光、特征点和同步情况。
9. 角度引导路径判断当前能不能拍、下一步该拍哪个角度。
10. 识别路径异步处理最新帧，不阻塞采集。
11. Jetson 路径把编码和推理交给硬件或独立进程。
12. 停止录制时先停新帧，再清缓冲，最后关闭文件。
13. 程序退出时释放摄像头、停止后台任务、避免资源悬挂。

如果面试官只是让你先简单介绍，可以先抛这段 40 秒版本：

> 项目启动后先看当前项目有没有摄像头配置。没有的话，就先发现设备，再把系统里的摄像头入口和项目里的相机编号绑定起来，防止插拔后顺序乱掉。采集开始后，每路摄像头都在后台出画面，同一帧画面会分到几条路：预览只拿最新帧，录制按顺序写视频和时间戳，质量评估看清晰度、曝光和特征点，识别只处理最新待识别画面。停止录制时也不是直接关文件，而是先停新帧，再把缓冲里的帧写完，最后刷新编码器和保存时间戳。

## 技术栈先讲准

这一节是专门防止“讲得很顺，但技术听起来不硬”。面试官如果追项目细节，你要能把这些技术名词和项目动作对应上。

| 技术点 | 项目里怎么用 | 面试时怎么说 |
| --- | --- | --- |
| PySide6 / Qt Widgets | 做桌面界面、多路预览、录制按钮、状态显示 | 我用的是 Python 版本 Qt，核心仍然是 Qt 的事件循环、信号槽和界面线程模型 |
| Qt 主线程事件循环 | 处理窗口绘制、按钮、定时器、跨线程通知 | 主线程只做轻量 UI，不直接碰摄像头读取、编码、推理 |
| QTimer | 按 33ms 左右节奏轮询最新帧，质量评估降低到约 0.5s 一次 | 预览不是每帧推界面，而是定时取最新帧，避免事件队列堆积 |
| QThread | 停止录制时做异步收尾 | 点停止后界面先进入“停止中”，真正排干队列和关文件放到后台做 |
| Python Thread | 每路摄像头一个采集线程，每路录制一个编码线程，识别也有后台线程 | 不是一个“大线程池乱跑”，而是按职责拆线程 |
| Queue | 预览、录制、同步监控使用不同队列 | 不同消费者目标不同，所以队列策略不同 |
| Event / Condition / Lock | 控制录制开关、暂停恢复、识别线程等待和共享状态保护 | 用同步原语控制状态，不靠 sleep 硬等 |
| V4L2 / USB | Linux 摄像头发现、参数控制、设备身份和带宽排查 | 摄像头不是普通文件，要考虑驱动、USB 拓扑和硬件编号 |
| OpenCV / PyAV | 图像处理、视频编码、帧格式转换 | OpenCV 更偏采集和图像处理，PyAV 更偏视频容器和编码 |
| GStreamer | Jetson 采集和硬件编码路径 | Jetson 上不能只靠 CPU，要走硬件能力 |
| Ultralytics / TensorRT | YOLO `.engine` 推理 | 推理放后台，只处理最新帧，避免反压采集 |
| 子进程推理服务 | Jetson 上隔离 Python、CUDA、TensorRT 环境 | 主程序和推理环境解耦，推理崩了也不该拖死界面 |

面试里可以这样补一句：

> 这个项目不是只用了一个“多线程”。它其实有几类线程：Qt 主线程负责界面，摄像头生产线程负责采集，编码线程负责录制，识别线程负责推理，停止录制还有专门的后台收尾线程。每类线程通过队列、事件和信号通知协作。

## 多线程调度怎么讲

这块是 Qt 面试最容易被追深的地方。不要只说“我用了多线程”，要说清楚线程之间怎么分工、怎么通信、怎么避免互相拖慢。

### 线程分工

| 线程/任务 | 负责什么 | 为什么要单独拆 |
| --- | --- | --- |
| Qt 主线程 | 界面绘制、按钮响应、定时器轮询、信号处理 | 界面线程不能被硬件读取和编码阻塞 |
| 摄像头生产线程 | 每路摄像头持续读取画面 | 某一路摄像头卡住，不应该拖住其他逻辑 |
| 录制编码线程 | 每路相机独立消费录制队列并写 MP4 | 编码和磁盘写入有波动，要和采集解耦 |
| 对齐监控线程 | 消费轻量时间戳信息，统计帧率和多路时间差 | 同步监控不需要复制大图，只看元信息 |
| 识别线程 | 后台跑目标检测，只保留最新待识别帧 | 推理慢于采集，不能让推理反压摄像头 |
| 停止录制线程 | 点停止后排干队列、刷新编码器、写时间戳 | 停止收尾可能耗时，不能卡主界面 |
| 启动探测线程池 | 程序启动时并行打开多路摄像头 | 多个摄像头串行打开太慢，也不利于发现启动失败 |

可以这样说：

> 我的线程模型不是简单“开几个线程”。主线程只负责 UI；每路摄像头有自己的生产线程；录制时每路相机还有自己的编码线程；识别单独跑后台；停止录制也异步做收尾。这样做的目的就是把硬件读取、视频编码、模型推理这几种慢任务隔开。

### 队列策略

这个项目里最能体现技术判断的其实是队列策略。

| 队列 | 容量/策略 | 适合回答什么问题 |
| --- | --- | --- |
| 预览队列 | 容量 1，新帧来时丢旧帧 | 为什么界面不卡，为什么预览可以丢帧 |
| 录制队列 | 按“缓冲秒数 × 帧率”计算容量，录制时阻塞写入 | 为什么录制要完整，为什么要看队列积压 |
| 同步监控队列 | 只放时间、来源、帧号等元信息，容量较小 | 为什么同步监控不复制大图 |
| 识别待处理区 | 每个摄像头只保留最新待识别帧 | 为什么 YOLO 不每帧都跑 |

面试官如果问“为什么预览队列是 1”，可以这样答：

> 预览只关心最新画面。队列越长，越可能显示历史帧。所以预览队列容量设得很小，新帧来了就覆盖旧帧。这个设计牺牲了预览完整性，换来了低延迟。

面试官如果问“录制队列为什么不能也这么做”，可以这样答：

> 录制不是给人看的实时预览，而是后续标定和重建的数据资产。它要尽量保留连续帧和时间戳，所以录制队列要有缓冲，不能像预览那样随便覆盖。

### 同步原语

这里可以补一点八股，但要讲回项目：

- `Event` 适合表示录制开关、停止信号、暂停恢复这种“状态门”。
- `Condition` 适合识别线程等待新帧，没有新帧时不空转，有新帧时被唤醒。
- `Lock / RLock` 适合保护共享状态，比如当前有哪些摄像头、队列映射、统计信息。
- `sentinel` 适合优雅停止消费者线程，比如录制队列里放一个空标记，告诉编码线程“后面没有新帧了，可以收尾”。

面试里可以这样说：

> 我没有用 sleep 去猜什么时候该停，而是用事件和队列标记做同步。开始录制时打开录制标志，停止时先清掉标志，让生产线程不再投递新帧，再给录制队列发送结束标记，编码线程收到后把剩余帧写完再退出。

### 面试官可能追的八股

**问：线程和进程有什么区别？**

> 线程共享同一进程的地址空间，通信成本低，但也更容易出现数据竞争；进程地址空间隔离，稳定性更好，但通信成本更高。这个项目里采集和录制适合线程，因为它们要共享帧队列；YOLO 在 Jetson 上有时适合独立进程，因为要隔离 CUDA、TensorRT 和 Python 环境。

**问：为什么不用线程池统一调度？**

> 线程池适合短任务，比如并行探测摄像头。摄像头采集和视频编码是长生命周期任务，而且每路设备有自己的状态和退出流程，所以我更倾向于固定线程模型，而不是把它们丢进通用线程池。

**问：Python 有 GIL，多线程还有意义吗？**

> 有意义。这个项目的线程不是为了纯 Python CPU 计算加速，而是为了隔离 I/O、摄像头读取、编码等待、模型推理调用和界面事件。很多底层库在 C/C++ 层执行，I/O 等待也不会一直占着解释器。这里多线程主要解决响应性和解耦，不是单纯追求 CPU 并行计算。

**问：怎么判断是不是队列积压？**

> 录制时会看每路录制队列深度。如果队列越来越深，说明编码或磁盘写入跟不上采集。这个时候不能盲目改 UI，要先判断是编码慢、磁盘慢，还是分辨率和帧率太高。

## YOLO 和 TensorRT 怎么部署

这块要讲得具体一点。不要只说“我用了 YOLO”，面试官会继续问模型怎么跑、在哪个线程跑、怎么避免卡界面、Jetson 环境怎么处理。

### 三种识别后端

| 后端 | 适用场景 | 面试说法 |
| --- | --- | --- |
| 启发式检测 | 没有模型环境时兜底 | 用传统图像方法先找主体区域，保证功能可用 |
| Ultralytics + TensorRT | 当前 Python 环境能直接加载 `.engine` | 用 YOLO 导出的 TensorRT 引擎做 GPU 推理 |
| 子进程推理服务 | Jetson 上主程序环境和 TensorRT 环境冲突 | Qt 主程序和推理环境隔离，通过进程间通信传帧和返回框 |

可以这样说：

> 识别这块我没有把 YOLO 直接塞进界面线程。项目里有一个异步识别器，界面轮询拿到最新帧后，按固定间隔提交给识别线程。识别线程每路相机只保留最新待处理帧，旧帧可以覆盖，避免推理队列越积越长。

### TensorRT 模型怎么来

面试里不用展开训练细节，但要说清部署链路：

1. 先有 YOLO 权重，比如 `.pt`。
2. 在 Jetson 或目标 GPU 环境导出 TensorRT `.engine`。
3. 配置推理后端、模型路径、输入尺寸、置信度阈值、目标类别和设备。
4. 运行时用 Ultralytics 加载 `.engine`，指定 `device` 和 `imgsz`。
5. 输出检测框后，再选一个最适合作为主体目标的框。

可以这样讲：

> YOLO 部署不是直接拿 `.pt` 在界面里跑。Jetson 上更适合提前导出 TensorRT `.engine`，运行时加载 engine 做推理。配置里会有模型路径、输入尺寸、置信度阈值、目标类别和 CUDA 设备。这样推理路径比较清楚，也方便切换后端。

### 为什么要子进程推理

这是很适合讲“工程落地”的点。

Jetson 上经常遇到一个问题：Qt 主程序希望用较新的 Python 环境，但 TensorRT、CUDA、PyTorch、Ultralytics 可能只在另一个环境里稳定。强行放在一个环境里，会让依赖管理很难受。

所以项目支持子进程推理：

- 主程序启动一个推理服务进程。
- 推理服务在专门的 Python 或 Conda 环境里运行。
- 主程序把帧压成 JPEG，再做 base64 编码。
- 通过标准输入输出传 JSON 行消息。
- 服务启动后先返回 ready。
- 每次请求包含帧序号和图片数据。
- 服务返回检测框、置信度、延迟和后端名称。
- 关闭时发送 shutdown，异常时保留 stderr 方便定位。

面试可以这样说：

> 我用子进程不是为了复杂化，而是为了隔离环境。Jetson 上 TensorRT 和 CUDA 依赖比较挑环境，主程序如果直接依赖它，界面稳定性和部署都会受影响。子进程模式下，Qt 主程序只关心请求和结果，推理环境可以单独维护。

### 为什么先 JPEG 再 base64

这个点面试官可能会觉得你确实看过实现。

> 因为进程间通过文本 JSON 行通信，不能直接塞 numpy 数组。先把图像压成 JPEG，可以减小传输体积；再 base64 编码，方便放进 JSON。代价是有一次压缩和解码开销，所以它适合低频异步识别，不适合每帧满帧率传输。

### 检测框怎么选

YOLO 可能输出多个框，项目不是随便拿第一个。更合理的选择是综合：

- 置信度。
- 目标是否靠近画面中心。
- 目标面积是否合理。

可以这样说：

> 我不是只拿 YOLO 的第一个框，而是会结合置信度、居中程度和面积比例选一个更像主体目标的框。因为这个项目里识别结果主要服务采集质量和构图判断，主体目标比“检测出很多框”更重要。

### YOLO 相关八股怎么接

**问：YOLO 为什么适合实时检测？**

> YOLO 是单阶段检测器，把候选区域生成和分类回归放在一次前向里做，速度比两阶段检测器更适合实时场景。这个项目里它只作为采集辅助，所以更看重延迟和稳定性。

**问：TensorRT 有什么作用？**

> TensorRT 是 NVIDIA 的推理优化框架，会做算子融合、精度优化和图优化，目标是让模型在 NVIDIA GPU 上跑得更快。Jetson 上资源有限，所以用 TensorRT engine 比直接跑原始 PyTorch 权重更合适。

**问：为什么不每帧都 YOLO？**

> 摄像头采集可能是 30fps，多路相机加起来帧数很多。YOLO 每帧都跑会排队，最后结果反而滞后。这个项目里识别是辅助功能，只需要最新结果，所以按间隔提交，旧帧覆盖。

**问：如果识别服务崩了怎么办？**

> 主程序不能被识别服务拖死。更稳的设计是识别初始化失败时降级到启发式检测，运行中服务异常时记录错误，界面继续采集和录制。识别是增强能力，不应该影响核心采集链路。

## 录制编码怎么讲

录制这块也要有八股，不然面试官会觉得你只是“调用库写视频”。

项目里有两条录制路径：

| 路径 | 用到的技术 | 适用场景 |
| --- | --- | --- |
| PyAV 路径 | Python 调 FFmpeg 生态，写 H.264 / MP4 | 普通桌面环境，调试方便 |
| GStreamer 路径 | OpenCV VideoWriter + GStreamer pipeline + Jetson 硬件编码器 | Jetson 上降低 CPU 压力 |

PyAV 路径可以这样讲：

> 普通桌面上，我更偏向用 PyAV 写 MP4。每路相机一个编码线程，第一次拿到帧时根据图像尺寸初始化视频流，把 BGR 转成 RGB，再交给编码器。停止时要 flush 编码器，把缓存包写进容器，再关闭文件。

GStreamer 路径可以这样讲：

> Jetson 上会走 GStreamer pipeline，大概是 appsrc 接收程序里的 BGR 帧，经过格式转换和 NVIDIA 视频转换，再交给硬件 H.264 编码器，最后经过 h264parse、qtmux 写成 MP4。这样能把编码压力从 CPU 转到 Jetson 的硬件编码器。

面试官如果问“MP4 为什么要收尾”，可以这样答：

> MP4 不是简单逐帧追加的裸文件，它有容器结构和元信息。编码器内部也可能缓存帧。停止录制时如果不 flush、不 close，可能文件尾部信息不完整，导致文件打不开或时间戳不完整。

## 流程一：启动和配置加载

这块面试官常会追问：

> 你的程序启动后第一步做什么？为什么需要配置？

先把场景说清楚：

这个项目不是每次启动都把机器上所有摄像头扫一遍然后直接打开。我的理解是，采集项目一旦确定下来，相机数量、相机角色、分辨率、帧率这些东西就应该尽量固定。第一次运行可以发现设备并生成配置，后面再启动就按这份配置恢复现场。

这里实际用到的技术：

- 项目级配置文件。
- Linux 摄像头设备发现。
- 相机业务编号。
- 分辨率、帧率、像素格式等采集参数。

我会这样解释原因：

多摄像头项目最怕的不是打不开，而是“打开了但顺序错了”。三维重建里每台相机都有自己的角色，比如左前、右前、顶部。操作系统给的设备入口可能会变，但项目里的相机身份不能跟着乱。

为什么不用启动时直接打开所有设备：

直接打开所有设备当然最省事，但它不适合这个项目。机器上可能插着不用的摄像头，设备枚举顺序也可能变，分辨率和帧率还可能不是上次采集的设置。短期能看到画面，长期很难保证输出数据可信。

如果他继续追问，可以这样接：

> 我会把配置理解成采集现场的约定。系统设备入口只是“这次操作系统怎么叫它”，业务相机编号才是“这个项目里它是谁”。录制文件、时间戳、标定和后续重建都要靠这个身份对齐。

## 流程二：摄像头发现和身份绑定

这块面试官常会追问：

> Linux 下多个 USB 摄像头怎么区分？直接用视频编号不行吗？

先把场景说清楚：

Linux 会给摄像头分配视频设备入口，但这个入口不是永久身份。你换个 USB 口、重新插拔、重启机器，顺序都有可能变。所以项目里不能只认这个入口，还要结合更稳定的硬件连接信息，再映射到自己的相机编号。

这里实际用到的技术：

- Linux 视频采集体系。
- USB 拓扑和硬件连接信息。
- 业务相机编号。
- 设备探测脚本和诊断报告。

我会这样解释原因：

录制文件后面要进入标定和三维重建，不是随便预览一下就结束。相机身份一错，后面可能把左侧画面当右侧画面，把顶部画面当正面画面。这个错误前面不拦住，后面很难靠算法补回来。

为什么不用系统临时编号：

系统编号只能说明“现在能从这个入口读到画面”，说明不了“它在我的采集任务里是哪台相机”。这是操作系统视角，不是业务视角。

如果他继续追问，可以这样接：

> 我会把“发现设备”和“确定身份”分开讲。发现设备解决的是有哪些摄像头能用，身份绑定解决的是这些摄像头在采集任务里分别代表谁。这两个问题混在一起，项目越跑越容易乱。

## 流程三：采集会话启动

这块面试官常会追问：

> 为什么采集要放后台？主线程直接读画面不是更简单吗？

先把场景说清楚：

多路摄像头会一直吐画面，但硬件这件事不完全受程序控制。某一路可能突然慢下来，USB 带宽可能不够，驱动也可能卡一下。如果界面线程直接等这些动作，按钮、窗口绘制、状态更新都会跟着卡。

这里实际用到的技术：

- 界面线程和后台采集线程分离。
- 事件通知。
- 每路设备独立采集。
- 采集状态统计。

我会这样解释原因：

Qt 的界面线程其实很忙，它要处理鼠标键盘、窗口绘制、定时器，还有后台发回来的通知。这个线程一旦被摄像头读取占住，用户看到的就是窗口没反应。

为什么不用主线程同步读取：

同步读取代码最直观，但代价也很明显：硬件慢，界面就慢；某一路设备超时，整个窗口就像卡死。对客户端来说，这个体验不能接受。

如果他继续追问，可以这样接：

> 我不是为了显得用了多线程才这么拆，而是因为摄像头读取本身就不稳定。界面线程只做交互和显示，采集线程去和设备打交道，中间用事件通知同步状态。

## 流程四：一帧画面进入系统

这块面试官常会追问：

> 画面读到以后，你怎么组织这帧数据？

先把场景说清楚：

一帧画面在这个项目里不能只当成一张图片。它要带着来源、帧序号、到达时间、当前帧率这些信息走下去。不然预览能做，但录制、时间对齐、质量评估都没法讲清。

这里实际用到的技术：

- 帧数据包。
- 单调时间戳。
- 帧序号。
- 相机来源标识。
- 最新帧缓存。

我会这样解释原因：

多路采集里，图片只是主体，元信息才是工程判断的依据。你要知道这帧从哪来、什么时候来、是不是跳帧了、跟其他相机差多少时间。没有这些信息，后面只能“看见画面”，但判断不了系统稳不稳。

为什么不用只传图片：

只传图片当然能显示，但面试官一问“有没有延迟”“有没有漏帧”“几路相机时间差多少”，就没法回答。所以我会把图像和元信息一起作为采集系统的数据单元。

如果他继续追问，可以这样接：

> 我不会把帧只理解成裸图像。裸图像适合显示，带时间和来源信息的帧才适合做录制、同步和排障。

## 流程五：预览路径

这块面试官常会追问：

> 为什么不每来一帧就刷新界面？

先把场景说清楚：

三路摄像头如果都是 30 帧，每秒就是 90 帧。四路就是 120 帧。你让界面每帧都刷新，听起来很实时，实际很容易把界面事件队列塞满。最后不是更流畅，而是用户一直在看旧画面。

这里实际用到的技术：

- 最新帧缓存。
- 界面定时刷新。
- 预览节流。
- 图像格式转换。
- 显示数据安全拷贝。

我会这样解释原因：

预览这条路的目标是“让我看到现在是什么样”，不是“每一帧都必须展示”。旧预览帧价值很低，追求它的完整性反而会把实时性拖垮。

为什么不用每帧推送界面：

每帧推送最大的问题是背压。后台产帧很快，界面绘制没那么快。排队一旦起来，界面看似还在刷新，其实是在消化历史帧。

为什么显示时要考虑内存：

还有一个容易被忽略的点是内存。后台采集缓冲可能很快被下一帧覆盖，而界面绘制不一定立刻发生。如果界面直接指向后台临时数据，轻则花屏，重则崩溃。

如果他继续追问，可以这样接：

> 预览这条路我更看重低延迟，不追求完整保存。旧画面对用户没什么价值，所以可以丢。录制那条路才追求完整性，这两个目标不能混在一个队列里。

## 流程六：录制路径

这块面试官常会追问：

> 预览和录制为什么要分开？一个队列不行吗？

先把场景说清楚：

录制这条路比预览重很多。它要把每路摄像头写成独立视频文件，还要保存统一时间戳。这里面有编码、磁盘写入、文件封装，任何一个环节都有波动。

这里实际用到的技术：

- 每路相机独立视频输出。
- H.264 编码。
- MP4 文件封装。
- 录制队列。
- 时间戳文件。
- 录制状态轮询。

我会这样解释原因：

预览和录制的目标天然不一样。预览要快，录制要稳。预览可以丢旧帧，录制不能随便丢。目标冲突的时候，就不能为了省事强行共用一条路径。

为什么不用一个队列：

一个队列的问题是互相拖累。写盘一慢，预览跟着慢；预览为了低延迟丢帧，又会伤到录制完整性。拆开之后，每条路按自己的目标处理，逻辑更清楚。

为什么要记录时间戳：

消费级 USB 摄像头一般没有统一硬件同步线，所以这里不能吹成硬同步。更准确的说法是软件时间对齐：每路独立采集，但把帧到达时间记录下来，后续标定和重建可以按时间去匹配。

如果他继续追问，可以这样接：

> 录制这块我不会只说“我能写 MP4”。更关键的是，视频文件和时间戳要一起可信。视频告诉你单路画面顺序，时间戳告诉你多路相机之间怎么对齐。

## 流程七：停止录制和文件收尾

这块面试官常会追问：

> 停止录制为什么不能直接把状态改成 false？

先把场景说清楚：

用户点停止的时候，系统不一定真的“空了”。队列里可能还有帧，编码器可能还有缓存，视频文件尾部还没写完，时间戳也要落盘。

这里实际用到的技术：

- 分阶段停止。
- 录制缓冲清空。
- 编码器刷新。
- 文件封装收尾。
- 时间戳持久化。
- 停止中状态。

我会这样解释原因：

所以停止录制不是一个瞬间动作，而是一个收尾流程。更稳的顺序是：先不再接收新帧，再把已经排队的帧写完，然后刷新编码缓存，最后关文件、保存时间戳。

为什么不用直接关文件：

直接关文件有时候看起来也能生成文件，但风险很大：视频尾部可能缺失，编码缓存可能没写完，时间戳可能不完整。最后用户看到的可能是文件打不开，或者视频能打开但帧数对不上。

如果他继续追问，可以这样接：

> 我会把停止录制理解成收尾，不是简单开关。开始录制前要准备好输出路径，停止录制时要把缓冲里的东西处理完，再关闭资源。

## 流程八：质量评估

这块面试官常会追问：

> 你说有采集质量判断，具体怎么判断？

先把场景说清楚：

三维重建对采集质量很敏感。画面太糊、曝光太差、纹理太少，后面都容易出问题。所以项目在实时预览时会算一些轻量指标，先给现场操作人员一个判断。

这里实际用到的技术：

- 清晰度评估。
- 亮度和过曝欠曝比例。
- 局部特征点数量。
- 多路时间差。
- 综合质量分数。

我会这样解释原因：

现场采集最怕的是“拍完回去才发现不能用”。这个质量评估不是要替代三维重建算法，而是提前把明显坏数据拦住，减少返工。

为什么不用在线三维重建实时判断：

在线重建确实证据更强，但它太重，延迟高，也容易受视角和纹理影响。Qt 界面里更需要稳定、快速、能解释的反馈，所以第一版用轻量规则更合适。

如果他继续追问，可以这样接：

> 我会把质量评估定位成现场预警，不是最终验收。它不追求判断百分百准确，而是用很低的成本把模糊、曝光差、特征少这些明显问题提前提示出来。

## 流程九：角度引导

这块面试官常会追问：

> 角度引导是怎么做的？为什么不自动识别物体角度？

先把场景说清楚：

这个功能的目的很朴素：让操作人员按 0、45、90、135、180、225、270、315 度把一圈拍完整。界面不需要显得很聪明，它主要要回答两个问题：现在这帧能不能收，下一步该拍哪个角度。

这里实际用到的技术：

- 固定角度桶。
- 当前帧质量分数。
- 已完成角度记录。
- 下一角度建议。
- 低质量重拍提示。

我会这样解释原因：

对三维重建来说，角度覆盖很重要。不是随便多拍几张就一定有用，漏掉关键角度照样会影响后面效果。固定角度桶能把流程管住，质量分数负责把明显不合格的画面挡一下。

为什么不自动估计角度：

普通 RGB 画面如果没有标记物、转台编码器、惯性传感器或者已知几何模型，自动估计物体角度并不可靠。更麻烦的是，系统一旦猜错，用户还以为已经拍完整了。

为什么不直接跑 COLMAP：

COLMAP 或在线稀疏重建当然更接近最终目标，但不适合塞进实时界面轮询里。界面要的是连续反馈，重建检查更适合放到采集后，作为离线验证。

如果他继续追问，可以这样接：

> 角度引导这块我不会吹成复杂算法。它更像是把采集流程标准化：先保证别漏角度、别收明显坏图，再考虑后面用更重的重建工具做验证。

## 流程十：目标识别路径

这块面试官常会追问：

> 识别为什么要异步？为什么不每帧都识别？

先把场景说清楚：

识别这块可能走 YOLO，也可能在 Jetson 上走 TensorRT。问题是推理通常跟不上采集速度，尤其多路画面一起进来时，不能让它反过来拖慢采集。

这里实际用到的技术：

- 异步识别。
- 最新帧覆盖。
- 后台推理。
- 结果短时间保持。
- 主程序和识别服务解耦。

我会这样解释原因：

识别路径更看重结果新不新，而不是每帧都算没算。如果每帧都排队，队列只会越来越长，最后界面显示的是几秒前的识别框，这对实时预览没意义。

为什么不用同步识别：

同步识别最大的问题是把推理耗时传给采集或界面。推理一慢，摄像头读帧、预览刷新、甚至录制稳定性都会被影响。

为什么只保留最新待识别帧：

旧帧的识别结果对实时界面价值不大。覆盖旧帧听起来像丢数据，但这里其实是在换低延迟，让结果尽量贴近当前画面。

如果他继续追问，可以这样接：

> 识别和录制不能用同一个标准看。录制要完整，所以不能随便丢；识别要新，所以可以跳帧。这个项目很多设计其实都是这种按目标取舍。

## 流程十一：Jetson 部署路径

这块面试官常会追问：

> Jetson 上为什么要单独设计？普通电脑能跑，为什么还要改？

先把场景说清楚：

Jetson Orin Nano 跟普通桌面不一样。它有 GPU、硬件编码器，也有一堆环境约束，比如 CUDA、TensorRT、Python 版本。项目在这条路径上会用 GStreamer 做摄像头输入，用 NVIDIA 硬件编码器写 H.264，用 TensorRT 做推理。

这里实际用到的技术：

- GStreamer 摄像头采集。
- Jetson 硬件 H.264 编码。
- TensorRT 推理。
- 独立识别进程。
- 混合分辨率采集。

我会这样解释原因：

边缘设备的资源没那么富裕。多路视频如果全靠 CPU 编码，CPU 很快就紧张。推理如果和主程序绑得太死，环境冲突或者模型卡顿都会影响采集稳定性。

为什么不用普通桌面方案硬跑：

普通桌面方案调试方便，但搬到 Jetson 上不一定合适。Jetson 的优势就在硬件编码和 GPU 推理，如果还按普通电脑那套全压 CPU，很容易变成 CPU 满载、帧率下降、界面卡顿。

为什么用独立进程跑识别：

Jetson 上 TensorRT、CUDA、PyTorch 和 Python 版本经常互相限制。把识别放到独立进程里，Qt 主程序可以保持自己的运行环境，推理服务用专门的环境。识别服务真出问题，也不应该直接把采集界面拖死。

如果他继续追问，可以这样接：

> Jetson 这块我会重点讲资源隔离。采集、编码、推理都不轻，一个环节卡住就可能影响全局。编码交给硬件，推理放后台或独立进程，Qt 主界面才能稳住。

## 流程十二：异常处理和性能定位

这块面试官常会追问：

> 如果某一路摄像头只有 15 帧，或者录制卡顿，你怎么排查？

这里千万别只说“我优化了多线程”。更像工程师的回答是按层排：

| 层次 | 可能问题 | 排查思路 |
| --- | --- | --- |
| 设备层 | 摄像头固件不稳定、曝光模式切换卡住 | 单独测试该设备，换普通 UVC 摄像头对比 |
| USB 层 | 带宽不足、同一 Hub 下设备太多 | 换 USB 口、换线、看 USB 拓扑 |
| 采集层 | 某路设备本身没有稳定输出 | 关闭录制和识别，只跑采集探测 |
| 编码层 | CPU 或硬件编码器吃满 | 降分辨率、降帧率、切硬件编码 |
| 磁盘层 | 写入跟不上 | 看录制队列是否积压 |
| 界面层 | 刷新太频繁、事件队列堆积 | 降低预览刷新频率，只取最新帧 |
| 识别层 | 推理太慢 | 异步识别，只保留最新帧 |

比较自然的回答：

> 我会先确认到底是摄像头实际只采到 15 帧，还是界面只显示了 15 帧。然后关掉录制和识别，只跑单路采集；单路正常，再逐步加多路、加录制、加识别。这样才能判断瓶颈在设备、USB、编码、磁盘、界面还是推理。

这段回答的好处：

它听起来不像在猜“代码慢”，而是在真的排系统问题。多摄像头项目里，很多锅不一定在业务代码，可能是 USB 带宽、驱动、摄像头固件、编码器或者设备环境。

## 流程十三：程序退出和资源释放

这块面试官常会追问：

> 程序退出时你怎么保证资源释放？

先把场景说清楚：

退出也不是小事。用户关窗口时，系统可能还在预览，可能正在录制，也可能有识别任务在后台跑。直接退出，摄像头句柄、视频文件、后台任务和识别进程都可能留下尾巴。

这里实际用到的技术：

- 统一停止流程。
- 后台任务结束等待。
- 摄像头资源释放。
- 文件收尾。
- 识别服务关闭。

我会这样解释原因：

多媒体程序很怕“窗口关了，后台还没停干净”。轻则下次打开摄像头失败，重则视频文件损坏或者进程残留。

为什么不用直接退出进程：

直接退出确实省事，但等于是把资源释放交给系统兜底。对视频文件、设备句柄、后台服务来说，这种兜底不够稳。

如果他继续追问，可以这样接：

> 我会把退出也当成流程的一部分。先停业务入口，再让后台任务完成收尾，最后释放资源。这样下次启动才不容易遇到设备被占用或文件损坏。

## Qt 机制怎么贯穿全流程

这一节是把项目流程和 Qt 八股连起来。

| Qt 机制 | 口语解释 | 项目里的落点 |
| --- | --- | --- |
| 事件循环 | 主线程持续处理用户操作、窗口绘制、定时器和跨线程通知 | 界面不能被摄像头读取、录制、识别阻塞 |
| 信号槽 | 对象之间的松耦合事件通知 | 后台采集状态通知界面刷新 |
| 线程归属 | 对象属于哪个线程，就应该在哪个线程处理自己的事件 | 后台不能直接操作界面控件 |
| 队列连接 | 跨线程通知进入接收方事件队列 | 后台发消息，界面线程排队处理 |
| 定时器 | 按固定节奏触发轻量任务 | 预览和质量评估按节奏取最新帧 |
| 对象生命周期 | 谁创建、谁拥有、何时释放必须清楚 | 摄像头、录制器、识别服务、界面对象不能互相悬挂 |

## Qt 八股怎么落到项目

这一节可以在面试官问“那你说说 Qt 原理”的时候用。不要把八股孤立背出来，要每个点都挂回项目。

### 1. 信号槽底层怎么理解

八股说法：

> Qt 的信号槽依赖元对象系统。带有元对象能力的类会在编译或绑定阶段保留对象、方法、信号等信息。信号发出后，Qt 根据连接关系找到接收者和槽函数，再决定直接调用还是投递到事件队列。

项目说法：

> 在这个项目里，采集、录制和界面之间就适合用这种事件通知。后台不关心界面上具体哪个控件要更新，只发“帧准备好了”“录制开始了”“停止完成了”这些状态，界面收到后自己处理。

为什么不用普通函数调用：

> 普通函数调用会让调用方知道接收方细节，而且跨线程时很容易变成后台直接改界面。信号槽更适合这种“后台产生状态，主线程消费状态”的模式。

### 2. 连接方式怎么讲

Qt 常见连接方式：

| 连接方式 | 简单理解 | 适合场景 |
| --- | --- | --- |
| 直接连接 | 发信号时立刻调用槽函数 | 同线程、轻量逻辑 |
| 队列连接 | 把调用投递到接收者线程事件队列 | 跨线程更新界面 |
| 自动连接 | Qt 根据发送方和接收方线程自动选择 | 大多数普通场景 |
| 阻塞队列连接 | 发送方等接收方处理完 | 少用，容易死锁 |

项目里怎么说：

> 这个项目里我最关心的是跨线程通知。后台线程产生状态以后，不应该直接改 UI，而应该让更新动作回到界面线程。队列连接的本质就是把这个调用变成接收者线程事件队列里的一个事件。

面试官追问“槽函数在哪个线程执行”：

> 不能只看信号从哪里发，要看接收者对象属于哪个线程。跨线程队列连接时，槽函数会在接收者所属线程的事件循环里执行。所以界面对象放在主线程，更新界面的槽也应该在主线程执行。

### 3. 事件循环怎么讲

八股说法：

> Qt 的事件循环负责分发鼠标、键盘、绘制、定时器、网络、跨线程通知等事件。主线程事件循环被阻塞，界面就无法响应。

项目说法：

> 摄像头读取、视频编码、YOLO 推理都不能放在主线程。它们任何一个慢下来，都会阻塞事件循环，最后表现出来就是窗口不刷新、按钮点了没反应。

面试官追问“为什么 QTimer 能工作”：

> QTimer 本身依赖事件循环。定时器到点后，不是系统凭空开线程执行，而是往对象所属线程的事件循环里投递定时事件。所以如果主线程被阻塞，定时器也会不准甚至不触发。

### 4. QThread 怎么讲

八股说法：

> QThread 对象本身通常仍然属于创建它的线程，真正的新线程从 run 函数开始执行。更推荐把耗时任务放到工作对象里，再移动到目标线程，避免误以为 QThread 对象在哪里，槽函数就一定在哪里执行。

项目说法：

> 这个项目里停止录制用了后台 QThread，是因为停止录制要排干队列、刷新编码器、写时间戳。这个过程不能卡主线程，所以界面先进入“停止中”，后台完成后再发完成信号让界面恢复。

面试官追问“为什么不用主线程 stop”：

> 停止录制不是瞬间动作。它可能等编码线程退出、写时间戳文件、关闭容器。主线程同步等这些动作，用户会以为软件卡了。

### 5. QObject 生命周期怎么讲

八股说法：

> QObject 有父子对象机制，父对象释放时会释放子对象；跨线程对象要注意线程归属；不能随便从另一个线程直接销毁还在处理事件的对象。

项目说法：

> 对这个项目来说，生命周期最重要的不是“窗口关了就算了”，而是采集会话、摄像头、录制器、识别服务都要有明确停止顺序。先停业务入口，再等后台任务收尾，最后释放资源。

### 6. QWidget 和 QML 怎么答

如果被问到 QWidget 和 QML，可以这样接，不要硬说自己都做过：

> 这个项目更适合 QWidget，因为它是偏工具型、控件密集的桌面采集软件，重点是稳定、调试方便、和底层采集状态绑定。QML 更适合动效更复杂、界面更现代的场景，但如果底层是多路视频和硬件调度，线程边界和数据流设计还是一样要处理。

### 7. Qt 多线程常见坑

| 坑 | 项目里怎么避免 |
| --- | --- |
| 后台线程直接改界面 | 后台只发状态，界面线程更新控件 |
| 主线程做耗时任务 | 摄像头、编码、识别、停止收尾都放后台 |
| 每帧都发 UI 更新 | 界面定时取最新帧 |
| 跨线程对象乱释放 | 退出时先停业务，再停后台，再释放资源 |
| 阻塞队列连接乱用 | 尽量用普通异步通知，避免互相等待死锁 |

### 信号槽怎么讲

不要只说“信号槽是观察者模式”。可以这样答：

> 在这个项目里，信号槽的价值是把后台状态和界面显示解耦。采集模块不需要知道界面上有哪些控件，它只发出“有新状态”或“录制状态变化”。界面收到后在自己的线程里更新显示。

为什么不用普通回调：

> 普通回调也能做，但跨线程时调用发生在哪个线程不够直观，容易让后台直接依赖界面对象。Qt 的事件通知更符合界面线程模型。

### 事件循环怎么讲

比较自然的回答：

> Qt 界面能响应按钮、绘制窗口、处理定时器，本质上都依赖主线程事件循环。摄像头读取、视频写入、识别这些任务一旦放进主线程，事件循环就没有机会处理界面事件，窗口就会卡。

为什么不用同步等待：

> 同步等待在命令行程序里可能还能接受，但在客户端程序里会直接变成卡顿。用户感知到的不是“程序正在努力处理”，而是“程序死了”。

### 跨线程更新怎么讲

比较自然的回答：

> 后台线程只负责产生数据和状态，不直接改界面。跨线程时把消息投递给界面线程，界面线程再更新控件。加锁只能解决数据竞争，不能改变界面对象应该由主线程操作这个事实。

为什么不用加锁直接改界面：

> 加锁保护不了 Qt 绘制事件、用户事件和后台修改之间的顺序关系。后台直接改界面，问题可能不是立刻崩，而是偶发、难复现。

## 技术决策总表

| 决策 | 选的方案 | 不选的方案 | 核心理由 |
| --- | --- | --- | --- |
| 界面和采集 | 后台采集，界面轻量刷新 | 主线程读摄像头 | 防止硬件阻塞拖死事件循环 |
| 后台通知界面 | 事件通知回主线程 | 后台直接改控件 | 遵守界面线程边界 |
| 预览刷新 | 定时取最新帧 | 每帧刷新 | 防止事件队列堆积 |
| 预览和录制 | 拆成两条路径 | 共用一条队列 | 低延迟和完整性目标冲突 |
| 录制停止 | 分阶段排干缓冲 | 直接关文件 | 防止视频和时间戳损坏 |
| 摄像头身份 | 硬件连接信息加业务编号 | 系统临时编号 | 防止插拔后相机错位 |
| 同步方式 | 软件时间戳对齐 | 宣称硬同步 | 消费级 USB 摄像头没有统一同步线 |
| 质量评估 | 轻量规则实时提示 | 在线三维重建 | 实时性、稳定性、可解释性更重要 |
| 角度引导 | 固定角度桶加质量分数 | 自动猜角度 | 无标记物时自动角度不可靠 |
| 识别 | 异步处理最新帧 | 每帧同步推理 | 防止推理反压采集 |
| Jetson 编码 | 硬件编码优先 | 全部 CPU 编码 | 降低边缘设备 CPU 压力 |
| Jetson 推理 | 独立环境或进程 | 强绑主程序 | 隔离依赖和故障 |

## 高频追问 20 题

下面这些不要逐字硬背。面试里更自然的方式是：先答结论，再补一句“我项目里就是这么处理的”，最后再讲取舍。

### 1. 介绍一下你的项目

> 我这个项目是一个多 USB 摄像头采集工具，主要服务三维重建前的数据采集。它不只是把摄像头画面显示出来，还要同时做多路预览、分路录制、时间戳记录、质量评估和角度引导。我在里面重点处理的是多路实时数据怎么调度，怎么让界面不卡、录制不断、相机身份不乱。

### 2. 这个项目最难的地方是什么

> 我觉得难点不是某个单独功能，而是这些功能的目标互相打架。预览要快，录制要完整，识别要新，质量评估要轻量。如果全放在一条链路里，一个慢任务就会拖住所有东西。所以我后来更关注数据流怎么拆，而不是简单把功能堆上去。

### 3. 为什么这个项目能体现 Qt 能力

> 因为它不是拖几个控件就结束。这个项目里有 Qt 客户端很典型的问题：界面线程不能被摄像头和录制阻塞，后台线程不能直接改界面，频繁刷新要节流，采集、录制、识别这些对象什么时候启动、什么时候释放也要想清楚。

### 4. 为什么不用主线程读摄像头

> 摄像头读取是硬件操作，不像普通内存计算那么可控。它可能阻塞，也可能某一路帧率突然掉下来。如果主线程去等它，Qt 的事件循环就没机会处理按钮、绘制和定时器，用户看到的就是界面卡住。

### 5. 为什么不用后台线程直接更新界面

> 界面对象最好还是回到界面线程里改。后台线程直接改控件，即使加锁，也只是保护数据竞争，解决不了 Qt 绘制事件和后台修改之间的顺序问题。我项目里更稳的方式是后台只发状态，界面收到后自己刷新。

### 6. 信号槽在项目里解决了什么

> 对我这个项目来说，信号槽不是为了“用 Qt 而用 Qt”，它主要解决两个事：一个是模块解耦，一个是线程边界。采集和录制不需要知道界面上有哪些控件，只要发状态；界面收到后在自己的线程里更新。

### 7. 为什么不每帧刷新界面

> 多路摄像头产帧很快，每帧都推界面，事件队列很容易堆起来。到后面界面看起来在刷新，其实是在显示旧帧。预览只关心最新状态，所以我更倾向于定时取最新帧。

### 8. 为什么预览可以丢帧

> 预览是给人现场看的，不是数据归档。用户要看的是现在摄像头有没有对准、画面清不清楚。旧预览帧价值不大，丢掉它可以换低延迟。

### 9. 为什么录制不能像预览一样丢帧

> 录制文件后面要用于标定和三维重建，它是数据资产。预览可以为了实时性丢旧帧，但录制要尽量保证连续性和时间戳完整性。

### 10. 停止录制为什么要等

> 点停止的时候，系统里可能还有没写完的帧，编码器也可能有缓存，文件容器还要写尾部信息。直接关文件风险很大，可能视频坏掉，也可能时间戳不完整。

### 11. 为什么要记录时间戳

> 因为这些消费级 USB 摄像头没有统一硬件同步。我们只能把每路帧到达系统的时间记下来，后续再按时间去做对齐。

### 12. 这算硬同步吗

> 不算硬同步。硬同步一般要外部触发线、统一时钟或者 genlock。我这个更准确地说是软件时间对齐，精度会受系统调度、USB 延迟和采集链路影响。

### 13. 摄像头身份怎么保证

> 我不会把系统临时视频编号直接当相机身份。它只能说明这次系统怎么分配入口，不能说明业务里它是哪台相机。项目里要用更稳定的硬件连接信息，再绑定自己的相机编号。

### 14. 图像显示为什么要考虑内存

> 因为界面绘制和后台采集不是同一个节奏。后台缓冲可能下一帧就被覆盖了，界面如果还指着那块临时数据，就可能花屏甚至崩溃。所以显示路径要保证数据生命周期安全。

### 15. 为什么质量评估不用深度学习

> 质量评估这块我第一版更看重实时和可解释。清晰度、曝光、特征点、时间差这些指标已经能做现场预警。深度学习当然可以做，但部署重，解释成本也高，不一定适合放在采集界面里。

### 16. 为什么角度引导不用自动姿态估计

> 没有标记物、转台编码器或者已知三维模型时，只靠普通 RGB 图像猜角度不太可靠。固定角度桶虽然朴素，但稳定，而且更符合现场采集流程。

### 17. 识别为什么不每帧都跑

> 推理通常比采集慢。每帧都跑，结果就是队列越排越长，最后识别框是旧画面的。实时系统里，新鲜度比“每帧都算过”更重要。

### 18. Jetson 上为什么用硬件编码

> 多路 H.264 如果全靠 CPU 编码，CPU 压力会很大，采集和界面都会受影响。Jetson 有硬件编码器，就应该把这部分压力转过去。

### 19. 为什么识别服务要和主程序隔离

> Jetson 上推理依赖 CUDA、TensorRT、PyTorch 和特定 Python 环境，和主程序环境不一定好合在一起。独立进程可以隔离依赖，也能避免识别服务崩溃后直接拖死 Qt 主程序。

### 20. 如果让你用 C++ Qt 重写，哪些设计不变

> 语言换成 C++ 后，对象所有权、智能指针、Qt 父子对象管理会更重要。但大的设计不变：界面线程和后台任务要分开，跨线程靠事件通知，预览和录制要分路，停止录制要收尾，相机身份不能靠临时编号。

## 技术深挖追问 15 题

这一组是二面更容易问的。回答时不要太长，但一定要说出机制。

### 1. 多线程具体是怎么调度的

> 主线程只做 Qt 界面和定时轮询。每路摄像头有独立采集线程，把帧分发到预览、录制和同步监控队列。录制开始后，每路相机还有自己的编码线程。识别有单独后台线程，只处理最新帧。停止录制也会放到后台 QThread 做收尾，避免主界面卡住。

### 2. 预览队列为什么容量是 1

> 因为预览只关心最新画面。容量越大，越容易积压历史帧，用户看到的反而不实时。容量 1 加丢旧帧策略，可以保证界面拿到的尽量是最新状态。

### 3. 录制队列容量怎么设计

> 录制队列按“缓冲秒数 × 帧率”估算容量，比如 30fps、6 秒缓冲就是大约 180 帧。这样编码或磁盘短暂抖动时不会马上丢数据，也方便通过队列深度判断写入是否跟不上。

### 4. 停止录制完整流程是什么

> 第一步清掉录制标志，让采集线程不再往录制队列投新帧。第二步给每路录制队列发送结束标记。第三步编码线程继续排干队列，flush 编码器，关闭容器。最后统一写时间戳文件并返回帧数和错误信息。

### 5. 为什么停止录制要用 QThread

> 停止录制可能等待编码线程退出、写时间戳、关闭文件，这些都可能耗时。如果主线程同步等待，界面会卡。所以用 QThread 做后台收尾，界面先显示“停止中”，完成后再通过信号回到主线程更新状态。

### 6. Python 有 GIL，多线程为什么还有用

> 这里多线程主要不是为了纯 Python 计算加速，而是为了隔离 I/O、摄像头读取、编码等待、推理调用和 UI 响应。很多底层库在 C/C++ 层执行，硬件等待也不会一直占 CPU。它解决的是响应性和模块解耦。

### 7. YOLO 是怎么部署的

> 先把 YOLO 权重导出成 TensorRT `.engine`，配置模型路径、输入尺寸、置信度阈值、目标类别和 CUDA 设备。运行时用 Ultralytics 加载 engine 做检测。为了不影响采集，推理放在异步识别线程里，并且按时间间隔提交最新帧。

### 8. 为什么 YOLO 不每帧都跑

> 多路摄像头帧率很高，YOLO 每帧都跑会排队。排队一长，识别结果就变成旧画面。这个项目里识别只是辅助采集，所以按间隔提交最新帧，旧帧覆盖，优先保证结果新。

### 9. 子进程推理服务解决了什么问题

> Jetson 上 CUDA、TensorRT、PyTorch、Ultralytics 和 Python 版本经常互相限制。子进程推理可以让 Qt 主程序用自己的环境，推理服务用专门环境。两边通过 JSON 行协议通信，推理服务崩了也不应该直接拖死采集界面。

### 10. 主程序和推理服务怎么传图

> 主程序把当前帧编码成 JPEG，再 base64 放进 JSON 消息，通过标准输入发给推理服务。服务解码成图像后做检测，再把检测框、置信度、延迟、后端名称通过标准输出返回。这样实现简单、跨环境稳定，但不适合每帧满速传输。

### 11. TensorRT 为什么比直接跑 PyTorch 更适合 Jetson

> TensorRT 会针对 NVIDIA GPU 做推理优化，比如算子融合、图优化、精度优化。Jetson 资源有限，直接跑 PyTorch 模型可能 CPU/GPU 压力更大，TensorRT engine 更适合部署阶段。

### 12. GStreamer 硬件编码路径怎么讲

> Jetson 上录制可以走 GStreamer pipeline：程序把 BGR 帧送进 appsrc，经过格式转换和 NVIDIA 视频转换，再交给 `nvv4l2h264enc` 硬件编码，最后经过 h264parse、qtmux 写成 MP4。这样能降低 CPU 编码压力。

### 13. PyAV 录制路径怎么讲

> 普通桌面上用 PyAV 写 MP4。第一次拿到帧时根据分辨率初始化视频流，把 BGR 转 RGB，再交给 H.264 编码器。停止时 flush 编码器，把缓存包写进 MP4 容器，最后关闭文件。

### 14. 如果录制队列一直涨，说明什么

> 说明消费速度低于生产速度，可能是编码慢、磁盘慢、分辨率帧率太高，或者硬件编码没走起来。排查时要看单路采集是否正常，再逐步加录制和识别，不能直接怪 UI。

### 15. 如果 YOLO 检测框很多，怎么选主体

> 不是简单取第一个框，而是综合置信度、目标是否靠近画面中心、面积比例是否合理。这个项目的识别结果是服务采集质量和构图判断，所以主体目标比检测出所有目标更重要。

## 两分钟项目讲解稿

这段不用背得一字不差。你可以按这个语气讲：

> 我做的是一个面向三维重建采集的多摄像头 Qt 工具。简单说，它不是只把摄像头打开显示出来，而是要在 Linux 下同时处理多路 USB 摄像头预览、分路录制、时间戳记录、质量评估和角度引导。
>
> 程序启动后会先加载当前项目的摄像头配置。如果没有配置，就先发现系统里的摄像头，然后把硬件连接信息和项目里的相机编号绑定起来。这样做主要是为了避免插拔之后系统视频编号变化，导致相机身份错乱。
>
> 采集开始后，每路摄像头都在后台持续出画面。画面进入系统后不会走一条大链路，而是分成几条路径：预览只保留最新帧，界面按固定节奏刷新；录制按相机分路写视频和时间戳；质量评估看清晰度、曝光、特征点和时间差；识别异步处理最新帧，避免推理反过来拖慢采集。
>
> 这个项目里我最关注的是工程取舍。预览追求低延迟，录制追求完整性，识别追求结果新，这几个目标不一样，所以不能简单共用一个队列。停止录制时也不能直接关文件，而是先停新帧，再写完缓冲，最后收尾编码器和时间戳。
>
> 如果部署到 Jetson，我会把视频编码尽量交给硬件，把识别放到后台或独立进程，让 Qt 主界面保持稳定。这个项目让我真正理解了 Qt 事件循环、跨线程通知、多路实时数据流、硬件设备调试和边缘部署这些东西不是孤立知识点，而是要放在同一条链路里考虑。
